# Worktree 收尾介面提案

本版取代上一版「查看變更／獨立更新／合回成果」三入口及新增同步 API 的提案，依使用者回饋只聚焦 **完成 worktree，選擇 Merge 或 Rebase 合回目標**。查看變更、獨立更新與建立工作從本收尾示意移除。

這是 macOS Orca 側欄的設計與[可點原型](../prototypes/worktree-flow.html)。使用者核准後已套用至正式面板原始碼，基準為 `main`／`596ce4a`。設計階段不需 SDLC；實作以 L2 紀錄於 [AISDLC-2026-1106-finish-merge-rebase-ui](/Users/devrune/Documents/code/ai-sdlc-hub/projects/orca-gitflow-hub/initiatives/AISDLC-2026-1106-finish-merge-rebase-ui/verification.md)。

## 一條收尾流程

1. 標題「完成工作」，固定顯示來源工作名稱、分支與資料夾，讓使用者知道正在收哪個 worktree。
2. 顯示 **來源工作 → 目標分支**，目標保留 Select，預填專案主要分支，不把 main 寫死。
3. 直接選 **Merge** 或 **Rebase**，預設 Merge。選項下各用一句話說明，不再增加三種結果代稱。
4. 有未提交內容時直接寫「會先提交全部 N 個變更檔案」，可展開檔案摘要；不是只提交勾選檔案，也不新增獨立查看功能。
5. 點「預覽 Merge／Rebase 收尾」，進入同一面板的專注確認步驟，固定來源、目標及方向，顯示影響摘要與必要提醒。
6. 點「確認 Merge／Rebase 到目標分支」才執行。返回修改保留選擇，但重新選目標、策略或清理設定後須產生新預覽。

## Merge 與 Rebase，只說清楚差別

| 選項 | 畫面上的一句話 | 此工具收尾時的行為 |
| --- | --- | --- |
| **Merge（預設）** | 保留原有提交，分歧時新增一個合併提交。 | 把來源成果合進目標，不因這個策略改寫來源既有提交。 |
| **Rebase** | 把來源提交接到目標後面，需要改寫時提交編號會變。 | 先重接來源提交，再快轉目標完成合回；Rebase 本身不等於合回。 |

兩者一般都保留每個提交，**Rebase 不等於 Squash**。目標沒有前進且符合快轉條件時，兩者都可直接快轉，不必改寫提交。真正會做的步驟以本次預覽為準。

下圖只用同一個「雙方都前進」的例子教差別，**不是目前專案的真實提交圖**。1、2 是來源工作原本的提交。

```text
合併前
A──B──C  目標 main
 ╲
  1──2   來源工作

Merge 收尾後
A──B──C──M  目標 main
 ╲      ╱
  1────2    來源工作

Rebase 收尾後
A──B──C──1′──2′  目標 main、來源工作
```

**Merge 保留分岔，用 M 接起來；Rebase 重新接上 1′、2′，工具再把目標推到 2′。**

## 其他選項與確認前必讀內容

- **Squash 收在「其他選項」**，不是第三個主策略。勾選「合成一個提交（Squash）」才整理提交數；所有改寫提醒在預覽前及確認頁可見。
- Merge＋Squash 分歧時仍可能再多一個合併提交；Squash＋Rebase 是整理成一個提交再合回，不保證無內容差異時目標仍新增提交。
- 需要重播、來源有合併提交且未選 Squash 時，本工具在預覽階段拒絕並提示改用 Merge 或 Squash。正式面板的 snapshot 沒有合併提交旗標，首頁 ahead／behind 也僅相對預設目標，因此不拿這些資料預先停用自選目標的 Rebase。這是原型到實作的差異；限制仍在執行前檢查，並非所有 Git Rebase 的通則。
- 「合併成功後移除工作資料夾」預設不勾，保留資料夾與分支。勾選時在確認前列出確切移除路徑，說明本機分支仍保留；失敗或 UNKNOWN 不清理。
- 確認摘要列出來源 → 目標、實際策略、全部未提交內容的處理、提交訊息、歷史改寫及資料夾保留／移除結果。沒有 remote-tracking 命中也不能當成從未分享，改寫提醒始終保留。
- 沿用 preview token、fingerprint、完整工作身分及內容核對，每次寫入動作一次確認。執行時禁止重送或切換；這個流程只更新本機，不自動 fetch、push 或遠端合併。

## 卡住時，保留下一步

| 狀態 | 呈現與恢復 |
| --- | --- |
| 載入／讀取失敗 | 保留來源身分，說明正在讀取或提供重新讀取；未知不能當成沒有變更。 |
| 終端或 AI 尚在使用 | 指出工作及可取得的具名終端／AI，提示先關閉再檢查，不代替使用者強制終止。 |
| 衝突／檔案阻擋 | 列出可取得的檔名、哪一步未執行與已完成內容，提供開啟該工作處理或返回修改策略。 |
| 成功／部分完成 | 分開列出已完成、失敗及未執行步驟，說明目標是否更新、資料夾是否保留。 |
| UNKNOWN | 保留現場與證據，先核對實際 Git 狀態，不提供直接重送，不保證自動還原。 |

Git 預檢成功不等於程式測試通過；圖、原型與綠色提示都不能取代真實 Git 結果。窄側欄先顯示影響摘要再確認，返回修改保留所有選擇，不並列一份重複長表單。

## 四個視角的取捨

創意：用同一張分歧圖說差別。推動：只留完成工作的路徑。邏輯：區分 Rebase 與工具後續快轉目標。質疑：簡化不能藏起改寫及移除後果。

| 維度 | 機會：創意＋推動 | 風險：邏輯＋質疑 |
| --- | --- | --- |
| 核心痛點 | Merge／Rebase 直接對照，少記一層代稱。 | 不能把 Rebase 說成合成一個提交。 |
| 執行方式 | 單一收尾頁，先預覽再確認。 | 未提交內容、改寫、清理仍要明示。 |
| 實作代價 | 映射既有 finish，不新增同步能力。 | 仍需驗證策略參數及所有阻擋狀態。 |

決策：採 Merge 預設、Squash 收合、資料夾預設保留。核心是讓使用者看懂兩個策略，無需選模式或先理解整套工作管理。
